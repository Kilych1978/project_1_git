# Отказ одного восстановленного окна — исправление 6.9.11

Проверены CRC всех шести присланных архивов и SHA-256 131 восстановленного
файла. Запуск 6.9.10 завершился без исключений и создал шестиканальный S16 WAV.
Применён базовый PCM-план; дополнительные улучшения отклонены до записи.

## Точная причина из отчёта

Сквозные проходы дали число отказов:
`114 → 11 → 7 → 4 → 7 → 3 → 3 → 1 → 1 → 1 → 1 → 1`.
В последнем плане оставалось 121 448 отметок улучшения на разных сетках,
но из-за единственного отказа сработал `COMPLETE_PLAN_FALLBACK`.
Это не 121 448 независимых мест фильма: сравниваются разные сетки и базы.

Повторялось одно окно:

| Поле | Значение |
| --- | ---: |
| target_time | 1028,354166666667 с |
| reference_time кандидата | 1028,351166666667 с |
| reference_time защищённой базы для того же target_time | 1028,352416117581 с |
| Разница центров | 1,249451 мс |
| micro_changed | false |
| change_extent_sec | 0 |
| Остаток «до» | −1,746311 мс |
| Остаток «после» | −1,781901 мс |
| Ложная разница модулей | 35,590278 мкс |

Окно 15,625 мс уже было целиком восстановлено к базе. Но `verify_render`
брал базовое окно через `base.forward(target_time)`, а ожидаемое/записанное —
через `final.forward(target_time)`. После восстановления аудио номинальные
часы намеренно не менялись. Поэтому измерялись разные участки эталона,
и отличие оценок превышало один отсчёт 48 кГц (20,833333 мкс).
Повторное расширение восстановления не могло исправить неправильное сравнение.

## Исправление

- `measure_window` принимает явный центр эталона. До, ожидаемый PCM и
  записанный PCM проверяются в одном диапазоне отсчётов. Абсолютная сетка
  также использует явный центр, без погрешности обхода inverse/forward.
- Кеш базовых измерений учитывает этот центр: результат для другого окна
  больше не используется при том же исходном target_time.
- При сравнении с восстановленной базой учитываются её реальные PCM-ветви,
  даже если номинальные карты совпадают.
- Проверки ухудшения и повреждённого WAV сохранены, включая случаи с
  `micro_changed=false`. Отказы не игнорируются по этому флагу.

## Прогресс

В PCM-поиске, виртуальных и записанных проверках строка содержит диапазон
эталона с миллисекундами:

```text
СКВОЗНАЯ ПРОВЕРКА PCM | проход 3/12 | исходник | сетка 2/2
[ 37.50%] … | эталон 00:15:12,098 → 00:15:12,223 | ETA 00:00:42
```

Стрелка означает «от — до», `,098` — 98 миллисекунд. Здесь длина окна —
125 мс. Сетка может проходить по всему фильму; показан текущий локальный
диапазон, а не искусственный многоминутный кусок. Позиции сохраняются
через объединённые счётчики разных сеток и при использовании кеша.
В терминале строка перерисовывается, ширина проверена для 80 столбцов.
После прохода выводятся число отказов и первые проблемные таймкоды.

## Диагностика

`PCM_PROPOSAL_MAP.json` сохраняет полное предложение до сквозных отмен.
В короткие фрагменты включаются также отказы сквозной проверки, даже если
последующий базовый WAV принят. Последние сохраняющиеся отказы имеют
приоритет. При наличии предложения добавляется `proposal_target.wav` —
виртуальное применение карты к текущему анализируемому первому каналу.
Это диагностический PCM, не обозначение проверенного итогового WAV.

Обычная синхронизация по-прежнему заново читает выбранные аудиофайлы.
Никакие карты или папки предыдущих запусков не загружаются автоматически.

## Проверки и ограничения

Регрессия воспроизведена на синтетическом звуке: восстановленный PCM
побитово определяется той же базой, а разные номинальные часы раньше
давали ложную разницу более одного отсчёта. Новый код сравнивает одно окно
и сохраняет независимое удалённое улучшение в настоящем шестиканальном WAV.
Отдельно проверено, что испорченный WAV всё равно отклоняется.

На десяти присланных восьмисекундных интервалах выполняется проверка с
полными координатами фильма и исходной фазой сетки. Кандидат строится из
плотных измерений текущего отчёта, записывается в S16 WAV и проверяется
относительно исходника и защищённой базы. Результаты:
[журнал и область проверки](TEST_RESULTS_RU.md).

Звука непосредственно из окна 17:08,351 в старом пакете нет. Причина
установлена по числовым картам и истории проверок, а само исправление
проверено на воспроизводимом аудиотесте. Новый сборщик диагностики сохраняет
такие окна. Полный новый фильм пользователя здесь не обработан.
